# ChatGPT Conversation Recovery Dynamics

## A client-side failure study, history-aware recovery model, and provider-friendly congestion design

**Repository paper / technical report**

### Abstract

This report analyzes a sanitized client-side capture of a ChatGPT conversation-loading failure. The public trace contains 108 paired stream/snapshot observations: 48 Accessible and 60 Blocked, with no mixed pairs. The observed Blocked regime is persistent and fast-failing. The first Accessible observation immediately following Blocked rebounded to Blocked in 8/8 observed cases, motivating a provisional Recovering state between Blocked and Healthy.

The cycle-time relation is approximately linear in service time, while the residual retains one-step temporal dependence. Independent one-change-point fits to service time align with the first Blocked observation in both active epochs. Local Monte Carlo and queueing stress models are then used to compare recovery architectures. The proposed design uses single-flight duplicate suppression, cheap state observation, start-anchored retry timing, recovery hysteresis, bounded server admission, and one expensive materialization only after stability evidence.

This work does **not** identify OpenAI's internal root cause or production topology. It is a reproducible client-side case study and falsifiable design exercise.

## Core model

~~~text
Z_n in {H, E, B}

Delta_n = S_n + mu + z_n + epsilon_n
z_n = phi * z_(n-1) + eta_n
~~~

where H is established Healthy/Accessible, E is provisional Recovering, B is Blocked, S is service/failure time, and z is a latent timing residual state.

## Core recovery design

~~~text
many local triggers
 -> single-flight owner
 -> cheap state/version observation
 -> start-anchored retry if blocked
 -> E / Recovering
 -> stable confirmation
 -> snapshot/delta once
 -> atomic reconcile
 -> optional realtime reattach
~~~
